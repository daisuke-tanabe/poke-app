# ポケモンデータ構造の複雑性について

このプロジェクトで扱うポケモンデータは一見シンプルに見えるが、実際には非常に複雑な構造を持っている。
この複雑性を理解せずに設計すると、後々大きな問題を引き起こす可能性があるため、ここに主要な複雑性を文書化する。

## 1. フォーム（Form）の複雑性

### 1.1 基本的なフォーム種類
- **通常フォーム**: 最も基本的な姿
- **色違い（Shiny）**: 色が異なるバリエーション
- **メガシンカ**: 戦闘中のみの一時的な進化形態
- **リージョンフォーム**: 地方によって姿・タイプが異なる

### 1.2 フォームの図鑑登録パターン

#### パターンA: 同じ図鑑番号を共有
```
例：ロトム（全国図鑑No.479）
- 通常フォーム
- ヒートロトム
- ウォッシュロトム
- フロストロトム
- スピンロトム
- カットロトム
→ 全て479番として扱われる
```

#### パターンB: 異なる図鑑番号を持つ
```
例：ライチュウ系統
- ライチュウ（通常）: 全国図鑑No.026
- ライチュウ（アローラのすがた）: 全国図鑑No.026だが、アローラ図鑑では別番号
```

#### パターンC: 完全に別種として扱う
```
例：リージョンフォームで進化先が異なる場合
- ガラルニャース: No.052
- ニャイキング（ガラルニャースの進化先）: No.863（完全に別種）
```

## 2. 図鑑登録の複雑性

### 2.1 全国図鑑 vs 地方図鑑
- **全国図鑑**: 全てのポケモンとフォームが登録される
- **地方図鑑**: その地方で出現するポケモンとフォームのみ登録

### 2.2 図鑑番号の複雑なルール

#### 同じポケモンでも図鑑によって番号が異なる
```
例：ピカチュウ
- 全国図鑑: No.025
- カントー図鑑: No.025
- ジョウト図鑑: No.022
- ホウエン図鑑: 未登録
```

#### 地方限定フォームの登録パターン
```
例：アローラライチュウ
- 全国図鑑: No.026（通常ライチュウと同番号）
- カントー図鑑: 未登録
- アローラ図鑑: No.027（独自番号）
```

### 2.3 複数図鑑への所属
- 同一ポケモンが複数の図鑑に所属可能
- 各図鑑で異なる番号を持つ可能性
- フォーム単位で図鑑登録が管理される

## 3. タイプの複雑性

### 3.1 フォーム別タイプ
```
例：ロトム
- 通常フォーム: でんき・ゴースト
- ヒートロトム: でんき・ほのお
- ウォッシュロトム: でんき・みず
```

### 3.2 図鑑別タイプエントリ
- 同じフォームでも図鑑ごとにタイプエントリが作成される
- 検索機能で「カントー図鑑の火タイプ」のような条件指定が必要なため

## 4. データベース設計への影響

### 4.1 制約の問題
- 図鑑番号の重複を完全に防ぐ制約は設定できない
- フォーム単位での重複も、運用上必要になる場合がある
- 結果として、データベースレベルでの制約は最小限にとどめ、アプリケーションレベルで整合性を管理

### 4.2 検索の複雑性
- 全国図鑑検索: 全てのポケモン・フォームを対象
- 地方図鑑検索: その図鑑に登録されたポケモン・フォームのみ対象
- タイプ検索: 図鑑とフォームの組み合わせでタイプを判定

## 5. 将来の拡張性への配慮

### 5.1 新しいフォーム種類への対応
- ゲームの新作で新しいフォーム概念が追加される可能性
- 柔軟なスキーマ設計により対応

### 5.2 図鑑システムの変更
- 新しい地方の追加
- 図鑑システム自体の仕様変更
- データベース制約を緩くすることで変更に対応しやすくする

## まとめ

ポケモンのデータ構造は、一見シンプルに見えて実は非常に複雑である。
この複雑性を理解し、柔軟性を重視した設計を行うことで、
将来的な仕様変更や新しいゲーム要素の追加にも対応できるシステムを構築できる。

データベース制約を最小限に抑え、アプリケーションレベルでデータ整合性を管理するアプローチは、
この複雑性に対する合理的な解決策である。
